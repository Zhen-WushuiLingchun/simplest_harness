# 预注册修订 2：取消竞争性资源上限并启用精确会话续跑

关联预注册：`2026-08-12-deepswe-v1.1-crossrepo20-preregistration.md`

关联修订：`2026-08-12-deepswe-v1.1-crossrepo20-amendment-1.md`

修订时间：`2026-08-12T21:39:00+08:00`

## 触发证据

正式 campaign 在冻结时已经产生 `13` 个有效计分结果：`3` pass、`10` fail；另有
`4` 个活动 trial 被可逆暂停，未开始的 trial 尚未调度。此前三个失败 trial 精确终止于
`model call budget exhausted: 200`：

- `boa-hierarchical-evaluation-cancellation`
- `dynamodb-toolbox-lazy-recursive-schemas`
- `effect-sse-httpapi-streaming`

三者都完成过非空的编辑、测试或诊断轨迹，但 Pier 收集到的 `artifacts/model.patch` 均为
`0` bytes。原因不是“模型未做工作”，而是 TMSH 在第 `200` 次模型调用后失败退出，模型尚未
提交工作；Pier 只收集相对基线 commit 的已提交 diff。旧 CLI 同时没有为 `tmsh run` 创建
session，因此容器被删除后不能逐消息恢复完整模型状态。

公开同题 mini-swe-agent 的 `n_agent_steps` 也表明 `200` 不是中性的截止点：Boa 的四次为
`255, 236, 208, 272`，DynamoDB Toolbox 为 `287, 275, 254, 211`，Effect 为
`228, 253, 216, 249`。在这三题上公开结果分别为 `3/4`、`4/4`、`1/4`。

## 修订内容

本修订由用户在看到上述结果后明确要求，因而属于**观察结果后的资源策略变更**，不得伪装成
原预注册设置：

1. 后续和续接 trial 不再使用 `200` 次竞争性模型调用上限。`maxModelCalls` 改为 `4096`，
   仅作为失控循环的事故熔断；它不是期望模型用满的预算，也不是成功判据。
2. agent execution timeout 从 `5400 seconds` 改为 `86400 seconds`，同样只作为事故熔断。
3. `tmsh run` 在首个模型调用前自动创建并打印本地 session，随后在完整模型/工具轮与成功
   压缩边界原子保存完整 `ModelMessage[]` 和 preservation ledger；`--resume ID` 按完整
   UUID 或唯一前缀接续。
4. 已经在内存中运行的 Pebble 和 Testem trial 不重启；其 `run.maxCalls` 在下一次循环预算
   检查处从 `200` 原地改为 `4096`。Numba 只等待 verifier，Updo 尚在环境构建，不受模型
   调用上限影响。
5. 三个已退出且容器已删除的 trial 不可能恢复 provider 未返回的隐藏状态，也没有旧版
   session 可载入。恢复只允许使用归档事件、命令输出和已观察修改重建工作状态，再以一次
   明示的 continuation handoff 接续；不得声称这是逐消息无损恢复。

## 分析边界

- 原设置下完成的 trial 保留原始 TMSH commit、上限、token、rollout、patch 和 verifier
  结果，不重写历史。
- 最终报告分别给出 `pre-amendment` 与 `continuation/unbounded` 分段；如给出总体结果，必须
  同时标注这是观察结果后修改资源策略的探索性结果，不再是原始冻结设置的 confirmatory
  估计。
- 同题模型固定为标准 DeepSeek API 的 `deepseek-v4-flash`；任务、Node `24.19.0`、
  pnpm `11.21.0`、网络 allowlist、YOLO、delegation depth `0` 和 verifier 均不变。
- 最终比较必须同时报告 reward、F2P/P2P/Partial、`n_agent_steps`、input/output/cache tokens、
  TMSH commit、修改文件和 git state；不得把负面结果压缩成模糊结论。

## 精确下一验证步骤

运行完整 TMSH 门禁并冻结新 commit；随后在出口仍暂停时验证两个活动进程的运行时上限补丁
从 `200` 变为 `4096`，再解除容器暂停，让它们自然完成。完成后重启 Pier 以载入新 adapter，
并从三份归档轨迹生成 continuation handoff，而不是重新探索任务。

## 执行后观测：运行时补丁失败并触发恢复分支

上述“原地改活进程”验证没有成功，负面结果必须保留：Node inspector 能在
`file:///root/tmsh/dist/runtime/run-engine.js` 的循环位置安装 breakpoint，但 Pebble 正在
执行长 Go 测试，Testem 正阻塞于 provider 请求，二者都没有在冻结期间到达下一次循环检查。
解除出口暂停后，两个旧请求均在 provider 成功响应的处理阶段失败：

- Pebble：`161` requests、`160` responses、终态 `failed`、`modelCalls=160`，错误精确为
  `Failed to process successful response`。
- Testem：`47` requests、`46` responses、终态 `failed`、`modelCalls=46`，错误精确为
  `Failed to process successful response`。

它们不是模型/任务计分失败，也未进入分母。容器删除前已保存并验证 recovery bundle；
Pebble 还保存 `25917` bytes tracked patch、`durability.go` `18164` bytes、
`durability_test.go` `14784` bytes，Testem 保存 `16655` bytes working patch 和
`3199` bytes AGENTS patch。Updo 在旧 Pier 终止前产生 `12` requests、`11` responses、
`22` tool calls，但 worktree 仍干净；Vitest 为 `0` events，视为未开始。

Numba 不受该恢复失败影响，已由原 Pier 正常收集为有效结果：TMSH `done`、`89` steps、
F2P `25/29`、P2P `827/827`、Partial `0.995327102803738`、Reward `0`、input
`13240085` tokens、cache read `13138688` tokens、output `137826` tokens，TMSH commit
仍为 `709ed7905aea0ac95d4d9c5d094a7e1c9f0e406a`。

因此后续不再修改旧进程内存。Boa、DynamoDB Toolbox、Effect 三个 cap 终态从正式分母
移入带逐文件 SHA-256 的 `amendment-2-resource-cap-continuations` 归档；恢复 trial 使用一次性
claim，加载局部代码 patch（如果仍存在）和由完整事件生成的 continuation handoff。该做法
保留已完成工作，但仍明确不是 provider-hidden reasoning 的逐消息无损恢复。
